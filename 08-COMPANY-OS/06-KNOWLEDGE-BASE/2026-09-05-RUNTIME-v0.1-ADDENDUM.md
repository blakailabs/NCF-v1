# Company OS Knowledge Base — Runtime v0.1 Addendum

**Date:** 2026-09-05

## New canonical implementation decisions

### Materialization is deterministic

The CFHS materializer is infrastructure, not an AI agent. Given the same normalized CDM and materializer version, it should produce equivalent logical mappings. AI may assist discovery before materialization, but does not improvise filesystem authority during installation.

### Materialization does not grant authority

The materializer represents authority already resolved in CDM. The existence of a principal, application, device, or file does not grant permission to use it.

### Staged activation

A new CFHS root is built in a staging namespace and activated only after verification. The v0.1 reference implementation refuses to overwrite an existing target.

### Source provenance is preserved

The complete source CDM is archived in the generated namespace for provenance. Canonical CFHS views are derived from the validated manifest rather than replacing the evidence chain.

### Secret values remain outside CFHS manifests

Credential-bearing fields must use opaque `secret://` references or approved placeholders. Inline secret-like values are rejected by the reference materializer.

## Kernel API contract

The Company Kernel API is now specified as the privileged boundary for user-space workloads.

Every privileged request is attributable to an actor, process, and trace. Authorization returns one of:

```text
ALLOW
DENY
ELEVATION_REQUIRED
```

Device invocation conceptually follows:

```text
REQUEST
  ↓
AUTHORIZE
  ↓
RESERVE RESOURCE BUDGET
  ↓
LEASE REQUIRED SECRET
  ↓
INVOKE DEVICE ADAPTER
  ↓
RECORD RESULT
  ↓
EMIT EVENT + AUDIT
  ↓
RELEASE / COMMIT RESERVATION
```

The OpenAPI document is a machine contract, not yet a production kernel implementation.
